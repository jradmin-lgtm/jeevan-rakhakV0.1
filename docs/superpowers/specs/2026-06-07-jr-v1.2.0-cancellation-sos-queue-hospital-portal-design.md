## 0. Hard constraints (non-negotiable for this batch)

1. **Zero regression of the v1.1.x build.** The team confirmed the current build is "perfect." Every change here is **additive** — new tables, columns, routes, screens, route-groups. No behavior change to: Google login/KYC restore, normal booking, accept→arrived→pickup→complete, fare quote, payment, admin dashboard, the existing SOS cascade dispatch, push registration. Diffs touch only what a CR requires.
2. **Pre-commit audit gate (CONTEXT.md §0-OPS)** runs before commit: (a) security-leak scan, (b) full end-to-end wiring of every new endpoint/event/screen, (c) no-regression typecheck + manual flow pass, (d) no stale timers/process/socket leaks. Record pass/fail in the commit message + VERSIONS.md.
3. **Schema migrations are additive and fail-loud** — `ADD COLUMN IF NOT EXISTS` / `CREATE TABLE IF NOT EXISTS` in the api-server bootstrap block; on failure `process.exit(1)` (never catch+warn — codified rule).
4. **API contracts stay backwards-compatible** — existing responses keep their existing fields; new fields are additive.
5. **Secrets server-side only.** Admin key never reaches the browser (existing `/api/proxy`). New hospital JWT secret lives server-side; the browser only ever holds a scoped JWT in an HTTP-only cookie.
6. **Git:** branch `prod`, never `main`. Ask before `git push` / Render deploy / Vercel deploy.

## CR#2 — Controlled driver-initiated ride cancellation

### Data model
New table `booking_cancellations` (audit log; the booking already has `cancelledAt` + `CANCELLED` status):

| col | type | notes |
|-----|------|-------|
| `id` | uuid pk | |
| `bookingId` | uuid fk → bookings | |
| `driverId` | uuid fk → drivers | |
| `reasonCode` | text | one of the 6 codes below |
| `remarks` | text nullable | mandatory + min 10 chars when `reasonCode = OTHER` |
| `outcome` | text | `RE_DISPATCHED` or `CLOSED` (what the system did) |
| `createdAt` | timestamptz default now | |

Indexes: `(driverId)`, `(bookingId)`, `(createdAt)`.

### The 5 fixed reasons + Other (locked)

| reasonCode | Label | Type | Automatic outcome |
|------------|-------|------|-------------------|
| `PATIENT_NOT_AVAILABLE` | Patient not at pickup location | Patient | **CLOSED** — booking → `CANCELLED`, patient push *"The ambulance driver was unable to locate you at the pickup location. Please create a new request if assistance is still required."* Driver → `AVAILABLE`. Gated behind wait timer. |
| `PATIENT_NOT_RESPONDING` | Patient not responding to calls | Patient | **CLOSED** — patient push *"Your booking was closed because we couldn't reach you. Please create a new request if assistance is still required."* Driver freed. Gated behind wait timer. |
| `VEHICLE_BREAKDOWN` | Vehicle breakdown / mechanical failure | Vehicle | **RE_DISPATCHED** — clear `driverId`, booking → `REQUESTED`, re-enter dispatch (SOS cascade if `isSos`, else broadcast pool); patient push *"The assigned ambulance is unable to continue due to a vehicle issue. We are searching for another available ambulance."* |
| `TYRE_PUNCTURE` | Tyre puncture | Vehicle | **RE_DISPATCHED** (same as breakdown). |
| `CANNOT_REACH_PICKUP` | Can't reach pickup (road blocked / no access) | Operational | **RE_DISPATCHED** — send another unit; patient stays in system. |
| `OTHER` | Other (typed reason) | Free-text | **RE_DISPATCHED by default** (never silently strand a patient). `remarks` mandatory, min 10 chars, shown verbatim in admin log. Admin can manually close if the note indicates the patient cancelled. |

### Wait-timer gate (starts on selection, visible countdown)
The two **patient** reasons trigger a deliberate wait that **starts when the driver selects the reason** (not silently from arrival — that would let a long-parked driver instantly abandon). Flow:
1. Cancel Ride → reason sheet → driver picks "Patient not at pickup" or "Patient not responding".
2. A **5:00 live countdown** screen appears with a **"Call patient"** CTA and copy *"Please wait and keep trying to reach the patient. You can cancel once the timer ends."*
3. **"Confirm cancellation"** stays disabled until the timer reaches 0:00, then enables → confirm closes the ride + notifies patient.

**Server enforcement (the real gate):** entering the patient-reason wait records a server-side `wait_started` timestamp (a lightweight `POST /driver/bookings/:id/cancel/start-wait` returning `{ waitStartedAt, waitSeconds }`, or reuse `arrivedAt` if later). The `cancel` call is rejected with `cancel_wait_not_elapsed` unless ≥ `DRIVER_CANCEL_PATIENT_WAIT_S` (default `300`) has actually elapsed since `wait_started`. The client countdown is UX only; the server timestamp is authoritative and un-gameable.

Vehicle + operational + Other reasons have **no** wait — confirm immediately (a breakdown/puncture is immediate).

### API
- `POST /api/v1/driver/bookings/:id/cancel` — body `{ reasonCode, remarks? }`. Auth = driver JWT, must own the booking, booking must be in a cancellable state (`ACCEPTED`/`ARRIVED`; not yet `PICKED_UP` — once a patient is onboard, cancellation is admin-only). Validates reasonCode + remarks rules + wait gate. Writes `booking_cancellations`, performs the outcome (close or re-dispatch), emits socket events, sends patient push. Returns the resulting booking state.
- `GET /api/v1/admin/cancellations` — paginated log: ride displayId, driver name, ambulance #, time, reason label/Other-text, outcome.
- Driver cancellation **stats**: `GET /api/v1/admin/drivers/:id` gains `cancellationCount` + `cancellationRate` (cancels / accepted, trailing window); admin driver list flags drivers above a threshold (env `DRIVER_CANCEL_FLAG_RATE`, default `0.3`).

### Re-dispatch recovery
Re-using existing dispatch: vehicle/operational/Other-default outcomes call the same code path a fresh booking uses — `isSos` rides re-enter `sos-cascade`, normal rides re-enter the broadcast pool. The previous driver is added to that booking's exclusion set so the same broken ambulance isn't re-offered. Patient does **not** re-book.

### Driver app (TripScreen)
- "Cancel Ride" button (visible in `ACCEPTED`/`ARRIVED` only) → reason bottom-sheet listing the 5 reasons + Other.
- "Other" reveals a mandatory multiline input (min 10 chars, live char counter).
- Patient reasons show a disabled state + countdown until the wait timer elapses.
- On success: TripScreen closes, driver returns to Dashboard `AVAILABLE`.
- i18n: all new strings in en + hi dicts.

### Admin web
- New `/cancellations` page (under the existing admin nav) — the log table + the high-rate flag badge on the drivers list.

## CR#1 — Unified incoming request queue + SOS persistence

### Problem (current)
SOS arrives as a transient full-screen modal; a newer SOS overwrites the previous one; a dismissed/rejected SOS is unrecoverable; SOS rides aren't kept in the Incoming Requests list the way normal bookings are.

### Design — state-backed unified queue
- **Keep** the full-screen SOS alert (higher visual priority). It is now a *presentation layer* over the queue, not the source of truth.
- The driver app holds an **Incoming Requests array keyed by booking id** (not a single modal slot). SOS + normal bookings live in the same list.
- **No overwrite:** a second SOS adds a row; it never replaces the first. The full-screen flash shows the highest-priority unseen SOS; dismissing the flash leaves every row intact in the list.
- **Sorting:** SOS first (🚨 **SOS EMERGENCY**), then normal (🚑 **BOOKING**), each newest-first within group. SOS rows carry a badge + priority highlight; colour highlight is optional polish.
- **Per-row actions:** Accept / Reject. Reject is explicit and only removes that row.
- **Resolution / removal triggers (all five):** a row leaves the queue when the booking is `accepted` / explicitly `rejected` by this driver / `expired` (TIMED_OUT) / `reassigned to another ambulance` (driverId now set to someone else) / `backend-cancelled`. Detected via socket event **and** reconciled by the poll (below) so a missed socket never leaves a stale or lost row.

### Source of truth — extend the existing poll
v1.1 added `GET /api/v1/driver/sos-pending`. Extend/replace with `GET /api/v1/driver/incoming` returning **all active requests visible to this driver**: SOS bookings dispatched to them still `REQUESTED` (with no reject row) **plus** normal broadcast bookings still `REQUESTED` in their pool. The driver app polls it on the existing tick (~8s) and reconciles the local queue (add new, drop resolved). Socket events update instantly between polls; the poll is the safety net. (`sos-pending` kept as an alias for one version for backward-compat, then removed.)

### Driver app
- `DashboardScreen`: render the unified queue from the reconciled array; SOS-first sort; badges; scrollable; per-row Accept/Reject.
- Full-screen SOS modal: triggered by the highest-priority unseen SOS; "dismiss" marks it seen (stays in list) — does **not** reject.
- No new timers without teardown (audit gate item 4): the poll already exists; the modal subscription clears on unmount.
- i18n: badge/label strings in en + hi.

### Backend
- No new dispatch behavior — purely a *visibility/persistence* change. SOS cascade, first-accept atomic lock, and loser-notification already exist and are unchanged. The only backend addition is the `/driver/incoming` aggregate read.

## CR#3 — Hospital portal (main build)

### Auth model (locked: per-hospital login + RBAC, same Vercel app)

**Data model** — add to `hospitals` table:
- `portalUsername` text unique nullable
- `portalPasswordHash` text nullable (bcrypt)
- `portalEnabled` boolean default false

(One credential per hospital for the pilot. A `hospital_users` table for multiple logins per hospital is explicitly deferred — YAGNI.)

**API auth:**
- `POST /api/v1/hospital/login` `{ username, password }` → bcrypt verify against the hospital row → issue **JWT `{ hospitalId, role: "hospital" }`** signed with new env `HOSPITAL_JWT_SECRET` (TTL 8h). Rejects if `portalEnabled` false.
- New `requireHospital` Fastify guard: validates the JWT, attaches `req.hospitalId` **from the token claim only**. No hospital-scoped endpoint ever reads a hospital id from the query/body — this is the RBAC core that makes cross-hospital access impossible.

**Hospital-scoped read endpoints** (every query filtered `WHERE destHospitalId = req.hospitalId`):
- `GET /api/v1/hospital/me` — hospital profile (name, address) + driver/ambulance counts (total linked via `driver_hospitals`, online + on-trip from `driver_heartbeats`/`drivers.status`).
- `GET /api/v1/hospital/bookings` — **live incoming queue**: active rides (`ACCEPTED`/`ARRIVED`/`PICKED_UP`) destined to this hospital. Per row: rideId (displayId), patient name/age/gender, emergency type, ambulance # (`driver.vehicleNumber`), driver name, paramedic name (= `resolveParamedic(booking)`), pickup location, status, ETA, distance remaining.
- `GET /api/v1/hospital/bookings/:id` — full unified medical record for one ride; **404 if `destHospitalId !== req.hospitalId`**. Sections: **A** patient-submitted (name, age, gender, emergency type, condition, notes), **B** paramedic assessment (conscious/severity/bleeding, BP/pulse/resp, observations/first-aid/treatment/notes — from `paramedicAssessment` JSONB), **C** live transit (ambulance location, ETA, distance, status, the 8-step workflow position).
- `GET /api/v1/hospital/drivers` — drivers tagged to this hospital + live online/on-trip status.
- `POST /api/v1/hospital/bookings/:id/acknowledge` — the loop-closer toggle (see below). Scope-checked.

**Data scope (locked):** hospital sees the above for **their** rides only. Hospital **never** sees: the platform users-accounts list, other users' profiles/history, other hospitals' rides/drivers/ambulances, or any platform-wide ops data. No `/admin/*` endpoint is reachable with a hospital JWT (separate guard, separate proxy without the admin key).

### Web (same admin-web Vercel app)
- Public `/hospital-login` page (outside the admin login).
- New `(hospital)` route group with its own layout (hospital branding, scoped nav) + `jr-hospital-session` HTTP-only cookie holding the JWT.
- New `/api/hospital-proxy/[...path]` — mirrors the admin proxy but forwards `Authorization: Bearer <jwt>` from the cookie and **does not** carry the admin key. A hospital session physically cannot reach admin endpoints.
- **Dashboard pages:**
  - **Live incoming queue** — cards/table of active inbound patients, SOS-flagged, status badges, ETA/distance, refreshing live.
  - **Patient record** (per ride) — unified A/B/C view; live-updating; "Acknowledge — team preparing" button.
  - **Live map** — reuses existing `MapEmbed` + OSRM route; ambulance position + route to hospital + ETA.
  - **Drivers/ambulances monitor** — counts: total linked, online, on-trip, in-transit.
  - **8-step status workflow** indicator on each ride: Request Created → Ambulance Assigned → Ambulance Arrived → Patient Picked Up → Assessment In Progress → Assessment Submitted → En Route to Hospital → Arrived at Hospital. Derived from booking status + `paramedicAssessment` presence + timestamps.

### Admin link (the thing you asked for)
On the admin hospital detail page (`/hospitals/[id]`), a new **"Hospital Portal"** section:
- Set / reset `portalUsername` + password (password sent to API, stored bcrypt; never displayed back).
- Toggle `portalEnabled`.
- **"Open hospital dashboard"** link → `/hospital-login` (or the dashboard). Admin → Hospitals → pick hospital → manage creds + open their scoped site.

### Realtime / sync
- Socket-server: hospital page authenticates the socket with its JWT and joins room `hospital:<hospitalId>`.
- Booking lifecycle events (accept / arrive / pickup / complete / cancel) and paramedic-assessment saves for rides where `destHospitalId = X` are emitted to `hospital:X`. The api-server already emits booking events to admin + driver/user rooms; we add a `hospital:<id>` emit for rides that have a destination hospital.
- **Poll fallback** (consistent with CR#1 philosophy): the dashboard also re-fetches `/hospital/bookings` on a ~10s tick so a missed socket never staleness-locks the board. No refresh required by the user.
- Teardown: socket leaves the room + poll clears on unmount (audit gate item 4).

## Paramedic resolver (locked decision)

No separate paramedic entity is built (deferred — it would be a net-new onboarding/login subsystem). Instead:
- A single helper `resolveParamedic(booking)` returns the assigned driver's name today.
- Every hospital-facing field is labelled **"Paramedic / Attendant"** and sourced through this helper.
- When real paramedics are later introduced, only `resolveParamedic` changes — API responses, dashboard, and medical record are untouched.

## Acknowledge toggle (locked decision)

The CR#3 "arrival preparation workflow" (ICU/OT/blood-bank/specialist prep) is treated as **informational** — we surface patient data early so the hospital's existing teams/systems prepare; we do **not** build bed/OT/blood-bank management (that's a hospital HIS, out of scope).

The one built loop-closer: `POST /hospital/bookings/:id/acknowledge` sets `bookings.hospitalAckAt` (new nullable timestamptz column) + optional `hospitalAckNote`. When set, the admin booking view and the driver's trip view show **"Hospital notified & preparing."** Emitted over sockets to admin + driver rooms. Gives the hospital a reason to use the board live, closes the loop end-to-end, near-zero scope.

## RBAC matrix

| Role | Surface | Can see | Cannot see |
|------|---------|---------|-----------|
| **Admin** | admin-web `(admin)` | Everything, platform-wide | — |
| **Hospital** | admin-web `(hospital)` | Only rides where `destHospitalId` = their id: patient clinical info, assigned driver/ambulance/paramedic, live tracking, their drivers' status. Acknowledge action. | Users-accounts list, other users' profiles, other hospitals' rides/drivers, platform-wide data, any `/admin/*` endpoint. |
| **Driver** | driver-app | Own profile, own trips, incoming queue (SOS+normal in their pool), own cancellation. | Other drivers, admin/hospital surfaces. |
| **User/Patient** | user-app | Own bookings/profile. | Everything else. |

Enforced at the API: admin key (admin), hospital JWT scoped by claim (hospital), driver/user JWT scoped by subject (apps). No surface derives its scope from a client-supplied id.

## Risks
- Highest regression surface of any JR ship (3 CRs + new role). Mitigation: audit gate, additive-only, per-surface commits even though it ships as one version.
- Hospital JWT is a new auth path — must verify no admin endpoint is reachable with it and scope is always claim-derived.
- Re-dispatch reuse must exclude the cancelling driver to avoid re-offering the broken ambulance.
- OSRM public demo has no SLA (acceptable for pilot; future self-host).
